## 1. Code / workflow

```
User complaint
   │
   ▼
create_agent (gpt-4o-mini, temp 0.7, system prompt with grounding rules)
   │   the model decides which tools to call, in any order, any number of times
   ├── check_hawkins_records(query)        → deterministic dict lookup   (FACTS)
   ├── gather_party_wisdom(question)       → deterministic dict lookup   (ADVICE)
   ├── cast_interdimensional_spell(problem, creativity_level) → random.sample (CREATIVE)
   └── consult_demogorgon(complaint)       → random.choice               (CHAOS)
   │
   ▼
Final answer (FACTS / ADVICE / CREATIVE IDEAS)
   │
   ▼
extract_trace()  → pairs every tool_call with its ToolMessage output
grounding_check() → support ratio + risk flags
   │
   ▼
lab_run_output.md
```

**Design choices**

- **Modern API:** `create_agent` from `langchain.agents` (LangChain 1.0), not `AgentExecutor` / `langchain_classic`.
- **Loop protection:** `recursion_limit=12` replaces the old `max_iterations`. A looping agent raises `GraphRecursionError`, which is caught and logged as an error.
- **Reproducibility:** `RANDOM_SEED=42` by default, so the random tools give the same picks on every run. Set it to empty for real chaos.
- **Grounding rule in the prompt:** facts may only come from `check_hawkins_records`. If it returns `NO RECORD FOUND`, the agent must say so.
- **Tool outputs are labelled:** records start with `RECORD H-00x` and party answers start with the member's name, so a reviewer can find each piece of evidence in the final answer.
- **Comparison:** `structured_pipeline()` runs the same tools in a fixed order (records → party → spell) with no LLM, as the "structured approach" baseline.

## 3. Analysis of agent behaviour

The full tables are in `lab_run_output.md` → *Analysis*. What to look for:

- **Which tools get used:** `check_hawkins_records` should come first for factual complaints (1–3, 5). `consult_demogorgon` and `cast_interdimensional_spell` should dominate the creative one (4, "high creativity").
- **Chaining patterns:** the order is not fixed. The model often calls several tools in parallel in one step, and sometimes adds a spell even when nobody asked for one.
- **Agent vs structured:**

| | Agent | Structured pipeline |
|---|---|---|
| Picks relevant tools | ✅ | ❌ always runs all 3 |
| Natural, combined answer | ✅ | ❌ glued raw outputs |
| Can add unsupported text | ⚠️ yes | ✅ no (no LLM) |
| Same output on rerun | ❌ (temperature + random tools) | ✅ (with seed) |

## 4. Failure / limitation

### Failure 1: the agent can produce a plausible but unsupported answer
**Complaint 5** ("The arcade machine at the Palace Arcade keeps eating my quarters. What does the official Hawkins file say about it?") has **no matching record**: there's no `arcade` key. The tool honestly returns `NO RECORD FOUND`. The risk is that the model fills the gap anyway (e.g. "The Hawkins file says the arcade is linked to the gate"). That would sound like lore, fit the theme, and have zero evidence behind it.

- **How it's detected:** `grounding_check()` flags `NO_RECORD`, and `INVENTED_RECORD` if the answer cites a record ID that the tool never returned. When I tested the pipeline with a simulated hallucinating model, the check caught it (support ratio 0.33, `INVENTED_RECORD` flag).
- **Real run result:** [PASTE: did gpt-4o-mini admit there is no record, or invent one?]

### Failure 2: keyword matching is brittle (found while testing)
`check_hawkins_records` and `gather_party_wisdom` only match if the **exact key** is a substring of the query. "A monster keeps eating my pumpkins" does **not** match `monsters`, and "move spoons with her mind" does not match `psychics`. Both returned `NO RECORD FOUND` when the full complaint text was passed in. It works when the model rewrites the query to the topic keyword, which is why the docstrings list the available topics. But the facts the user gets then depend on how the model phrases its query.

- **Fix (stretch):** match singular/plural and synonyms (`monster`, `creature` → `monsters`), or replace the dictionary with embedding-based retrieval and return a similarity score as evidence.

### Other grounding risks
1. **Random tools:** `consult_demogorgon` and `cast_interdimensional_spell` change between runs, so the same complaint gives different answers. That's acceptable for creative ideas, not for facts. The answer format keeps them apart (FACTS vs CREATIVE IDEAS), and the seed makes the proof reproducible.
2. **Blending:** the model may merge a random spell into the "facts" part, which makes a creative idea look like an official record. Check this in the verification table: every FACTS line must trace back to a `RECORD H-00x`.
3. **The support ratio is a rough heuristic:** it counts word overlap, so a paraphrase can score low while still being correct, and an answer can reuse evidence words to say something false. It points the reviewer at answers worth checking by hand; it doesn't prove anything.
